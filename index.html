Flow, hooks, bars — and end-to-end tests that hit.

Wayne Jones

Welcome. This talk is about end-to-end testing, told through the structure of a rap cipher. By the end, you'll have a mental model for writing test suites that are readable, maintainable, and resilient — and you'll see the whole loop live: tests written for behaviors, tests catching broken behaviors, and fixes making them pass.

Three acts

I The cipher — what a rap cipher teaches a test suite

II The instrument — a live demo site built for testing

III The tracks — five behaviors, five RED→GREEN arcs

Act I sets up the metaphor. Act II is the instrument we'll play — a small rap-album review site. Act III is the main event: five tracks, and each one follows the same loop — describe a behavior, write a test, watch it go RED, fix the app, watch it go GREEN.

ACT I

THE CIPHER

A cipher is a circle of emcees passing one microphone around. Each rapper gets the mic, spits a verse, and passes it on. If anyone drops it, the whole circle feels it.

What is a cipher?

  • A circle of emcees, one microphone
  • Each verse has flow — the rhythm of the journey
  • A hook — the part everyone sings back
  • Bars — the lines that land and stay with you
  • Cadence — timing so good nobody stumbles

"A good cipher has no filler. Every line earns its place."

The cipher works because everyone shares the same mic and the same beat. A good test suite is exactly the same: shared helpers, one consistent rhythm, and every single test earning its place. Let's map that onto testing.

The metaphor map

CipherTest suite

One microphone, shared by every verse: that's your fixture. Flow is the journey your test walks — the same path a user walks. Bars are the assertions, the lines that land. Cadence is the timing: waiting reliably for the app, not sleeping through it.

Why we need the structure

Too many suites are like an off-beat freestyle:

  • Tests nobody can read — 400 lines of setup
  • Tests that are flaky — they pass alone, fail in CI
  • Tests that assert implementation, not behavior

A well-produced album: tight structure, no filler, every line serving a purpose.

The structure of a cipher fixes all three: readable (named tracks, shared hook), resilient (behavior-level waits, cadence), maintainable (every test is a verse, not a novel). The rest of the talk proves it with a live app.

The rules of the cipher

Boombox Reviews rates every album on the classic 5-mic scale:

  • 5 mics — instant classic, plays on loop
  • 4 mics — certified heat
  • 3 mics — solid, a few bars of filler
  • 2 mics — one good single. Maybe.
  • 1 mic — straight to the bargain bin

The same scale applies to your tests — rate every test by whether it proves a real user behavior.

The 5-mic rule gives us a way to talk about quality — both for albums and for tests. A test that only proves a button exists is a 2-mic test. A test that proves a user can complete a real journey is a 5-mic test. In Act III we only write 5-mic tests.

ACT II

THE INSTRUMENT

Every cipher needs a stage. Ours is Boombox Reviews — a real, working album review site that we will test like a record we're producing.

Boombox Reviews

  • Sixteen classic hip-hop albums, real cover art
  • Cards with 5-mic ratings and a "Read Review" trigger
  • A review dialog — keyboard-driven, like everything users expect
  • Built to be tested for behaviors — every track maps to one user behavior
The site is intentionally small: a header, a grid of album cards, and a review dialog. Small enough to demo live, real enough that broken behaviors are visible to anyone. Each behavior we test is something a real user actually does.

The hook — one mic, every verse


export const test = base.extend({
  boombox: async ({ page }, use) => {
    await use({

Every track starts the same way — the mic is already hot.

This is the hook — the part every verse drops into. A custom Playwright fixture that handles the boring, repetitive setup: navigating, opening a review, running an accessibility scan. Tests stop being 50 lines of setup and become pure behavior.

ACT III

FIVE TRACKS, FIVE ARCS

Every track: behavior → test → RED → fix → GREEN

The main event. Five tracks, and each one runs the exact same loop. I'll describe a real user behavior, show the test that describes it, watch it fail against the broken app, fix the smallest possible thing, and watch it pass.

TRACK 01

FLOW

Keyboard navigation: the user journey through the review dialog

Track 01 is flow — the journey. The behavior: a user opens a review with their keyboard, moves through the dialog, and leaves with Escape. Real users do this every day. If any part of the journey breaks, the flow breaks.

Track 01 — the behavior

A user opens the Illmatic review with the keyboard and:

  1. Focus lands inside the dialog when it opens
  2. Tab orbits inside the dialog — never the page behind
  3. Escape closes it and hands focus back to the trigger

Three sentences of behavior → three verses of test.

Notice what we don't say: no CSS classes, no component names, no implementation. Just the journey. That's a behavior — and behaviors are what users notice.

Track 01 — the verse

Three tests, each one bar of the verse. Read them out loud — they read like a spec of the behavior, not like code. That's the litmus test for a 5-mic test: a product person can read it and nod.

3/3 verses fail. The flow is broken — the test caught it.

Run the track: all three tests fail. Focus never enters the dialog, Tab runs free across the whole page behind it, and Escape does nothing. This is the point of the exercise: we designed tests for behavior first, so the broken behavior is caught the moment it happens — not when a user complains.

Track 01 — the fix


export function useFocusTrap(onClose: () => void) {
  useEffect(() => {
    const previouslyFocused = document.activeElement;
    focusFirst();

    const onKeyDown = (event: KeyboardEvent) => {
      if (event.key === "Escape") { onClose(); return; }
      if (event.key !== "Tab") return;

      const items = focusables();
      const first = items[0];
      const last = items[items.length - 1];
      const active = document.activeElement;

      if (event.shiftKey && active === first) {
        event.preventDefault(); last.focus();
      } else if (!event.shiftKey && active === last) {
        event.preventDefault(); first.focus();
      }
    };

    document.addEventListener("keydown", onKeyDown);
    return () => {
      document.removeEventListener("keydown", onKeyDown);
      previouslyFocused?.focus();   // hand the mic back
    };
  }, [onClose]);

  return containerRef;
}

One small hook: focus in → orbit → Escape hands the mic back.

The fix is one focused hook — the smallest thing that restores the flow. Focus lands on the first focusable element, Tab orbits the ends of the dialog, Escape closes it, and on unmount focus returns to whoever handed us the mic. True story: my first version of this hook had a bug of its own — a `??` fallback that always fired (focus() returns undefined), so focus kept landing on the dialog container instead of a real control. The same test caught it. That's the whole point: tests guard behavior, including the fixes.

TRACK 02

HOOKS

Accessibility flows: the parts everyone sings back

Track 02 is hooks — the accessible parts of a song, the part everyone can sing back. For a site, that's the parts assistive tech can reach: proper dialog semantics, contrast, alt text. The hook fixture makes scanning effortless.

Track 02 — the behavior

A screen reader user opens a review and hears:

  1. A named dialog — announced as a modal, not a mystery box
  2. Content that passes WCAG 2.2 AA — contrast included
  3. Every cover described by its alt text

Accessibility is a behavior. Treat it like one.

Accessibility isn't a checkbox — it's a behavior real users depend on. We test it exactly like Track 01: describe the experience, assert it.

TRACK 03

BARS

Visual stability: assertions that hold the layout to its word

Track 03 is bars — the lines that land. In design terms: the layout that holds its shape. A record doesn't jump forward when the snare hits, and a page shouldn't jump when an image finishes loading.

Track 03 — the behavior

A user on a slow connection scrolls the record bin and:

  1. Every card holds its box while covers stream in — no layout shift
  2. Every cover reserves its space from the first paint

Cumulative Layout Shift is a Core Web Vital. Bars measure it.

Layout shift isn't a cosmetic nit — it's a Core Web Vital (CLS). Users on slow networks click the wrong album because the grid moved under their cursor. The behavior: the layout must hold its shape no matter how covers load.

Track 03 — the verse


test.beforeEach(async ({ page, boombox }) => {
  // the hook: slow the covers down so we can see the grid at its worst
  await page.route("**/covers/*.jpg", async (route) => {
    await new Promise((resolve) => setTimeout(resolve, 1500));
    await route.continue();
  });
  await boombox.goto();
});

test("cards hold their box while covers stream in", async ({ page }) => {
  await page.evaluate(() => document.fonts.ready);
  const first = page.locator('[data-album="illmatic"]');

  const sizeBefore = await first.boundingBox();   // bare grid

  await expect.poll(async () => {
    const img = first.locator("img");
    return (await img.count()) > 0 &&
           (await img.evaluate((el) => el.complete));
  }).toBe(true);                                  // grid, fully loaded

  const sizeAfter = await first.boundingBox();
  expect(sizeAfter).toEqual(sizeBefore);          // the bars hold
});
The route interception is the cadence trick — we slow covers by 1.5 seconds so the test always sees the worst case: a bare grid and a fully loaded grid. Same box, exactly. No tolerance needed, because the behavior has no tolerance.

Track 03 — RED

The broken app lets covers push the page:

+   "height": 352.375,

One pixel, but every card does it — the whole grid jumps.

The diff is a single pixel — but it's every card, on every load, on every slow connection. Users feel it as a click into the wrong album. The test found it because we wrote the assertion for the behavior, not for our own eyes.

Track 03 — the fix


.album-art {
  aspect-ratio: 1 / 1;      /* the box is reserved up front */
  position: relative;
}

.album-art__image {
  position: absolute;       /* the cover fills the reserved box */
  inset: 0;
  width: 100%;
  height: 100%;
  object-fit: cover;
}

The image becomes an overlay on a reserved box — zero shift, forever.

One CSS pattern: the art box declares its aspect ratio before the image arrives, and the image simply fills it. The page can't shift, because there's no layout for the image to participate in. The bar holds.

TRACK 04

CADENCE

Resilient network handling: never stumble when the beat skips

Track 04 is cadence — timing that never breaks, even when the beat skips. For the app: what happens when a cover request fails? A good MC keeps flowing. A good site keeps reviewing.

Track 04 — the behavior

A user on a flaky connection opens the record bin and:

  1. A dropped cover shows a fallback tile — never a broken-image icon
  2. The site keeps reviewing even when every cover fails

The beat will skip. Flow is what you do when it does.

Networks fail. Covers 404, requests drop, CDNs hiccup. The behavior we want: the site degrades gracefully — a styled fallback, never a broken icon.

Track 04 — the verse


test("a dropped cover renders a fallback tile, not a broken image",
  async ({ page, boombox }) => {
    // cut the wire for one album
    await page.route("**/covers/madvillainy.jpg",
                     (route) => route.abort());
    await boombox.goto();

    const card = page.locator('[data-album="madvillainy"]');

    await expect(card.locator("[data-testid='album-art-fallback']"))
      .toBeVisible();
    await expect(card.locator("img")).toHaveCount(0);
    await expect(card).toContainText("Madvillainy");
  });

test("the site keeps reviewing when every cover fails",
  async ({ page, boombox }) => {
    await page.route("**/covers/*.jpg", (route) => route.abort());
    await boombox.goto();

    await expect(page.getByRole("heading", { name: /every album/i }))
      .toBeVisible();
    await expect(page.locator("[data-testid='album-art-fallback']"))
      .toHaveCount(albums.length);   // sixteen covers, sixteen tiles
  });
Network-level testing is what Playwright does best — we're not mocking a library, we're cutting the actual request on the actual page. Both tests describe the behavior: one cover down, or all sixteen down.

Track 04 — the fix

if (failed) {
  return (
    <figure data-testid="album-art-fallback"
            style={{ background: `linear-gradient(135deg,

<img src={src} onError={() => setFailed(true)} ... />

One error handler: the cover swaps to the album's colors.

The fix is one handler and one fallback render — the cover is replaced by a gradient tile using the album's own colors, still labeled with title and artist. The review experience keeps flowing.

OUTRO

FIVE BARS TO TAKE HOME

Thirty minutes of metaphor distilled into five bars you can take back to your own test suites on Monday.

Five bars to take home

  1. Flow — test the journey, not the page
  2. Hooks — one shared fixture, every verse drops into it
  3. Bars — assert behaviors, not implementation
  4. Cadence — wait for the real world; simulate its worst days
  5. No filler — every test earns its place on the album
Flow: if a human can't describe the journey, neither can the test. Hooks: setup is a fixture, not copy-paste. Bars: ask 'what does the user experience?', never 'what does the component render?'. Cadence: use route interception to test slow and broken networks. No filler: if a test never went red, it's proving nothing.

Write your own cipher


[]  Name your tracks after behaviors, not files
[]  One shared fixture (the hook) for setup
[]  Write the behavior in plain language first
[]  Watch it go RED before you write the fix
[]  Fix the smallest thing that restores the flow
[]  Watch it go GREEN — then keep it green in CI
A six-step checklist. The red step is the one people skip — but the red run is what proves the test actually guards the behavior. If it never went red, you don't know it can catch anything.
