SIDE A

THE CIPHER

A cipher is a circle of emcees passing one microphone around. Each rapper gets the mic, spits a verse, and passes it on. If anyone drops it, the whole circle feels it. Side A maps that onto test suites and sets up the mixtape — the structure every track of the talk will follow.

What is a cipher?

  • A circle of emcees, one microphone
  • Each verse has flow — the rhythm of the journey
  • A hook — the part everyone sings back
  • Bars — the lines that land and stay with you
  • Cadence — timing so good nobody stumbles

"A good cipher has no filler. Every line earns its place."

The cipher works because everyone shares the same mic and the same beat. A good test suite is exactly the same: shared helpers, one consistent rhythm, and every single test earning its place. Let's map that onto testing.

One microphone, shared by every verse: that's your fixture. Flow is the journey your test walks — the same path a user walks. Bars are the assertions, the lines that land. Cadence is the timing: waiting reliably for the app, not sleeping through it.

Why we need the structure

Too many suites are like an off-beat freestyle:

  • Tests nobody can read — 400 lines of setup
  • Tests that are flaky — they pass alone, fail in CI
  • Tests that assert implementation, not behavior

A well-produced album: tight structure, no filler, every line serving a purpose.

The structure of a cipher fixes all three: readable (named tracks, shared hook), resilient (behavior-level waits, cadence), maintainable (every test is a verse, not a novel). The rest of the talk proves it with a live app.

The rules of the cipher

Boombox Reviews rates every album on the classic 5-mic scale:

  • 5 mics — instant classic, plays on loop
  • 4 mics — certified heat
  • 3 mics — solid, a few bars of filler
  • 2 mics — one good single. Maybe.
  • 1 mic — straight to the bargain bin

The same scale applies to your tests — rate every test by whether it proves a real user behavior.

The 5-mic rule gives us a way to talk about quality — both for albums and for tests. A test that only proves a button exists is a 2-mic test. A test that proves a user can complete a real journey is a 5-mic test. On Side B we only write 5-mic tests.

A test suite is an album: tracks, not files.

The mixtape closes Side A: each track is a test file, named after the behavior it protects — the real file tree lives in tests/ in the demo repo. When a track is red, you know which song is skipping — you don't have to debug the whole album. And every track starts the same way: one shared fixture (the hook, tests/fixtures/site.ts) does the setup — open the crate, open a review, run an axe scan. You'll see it live on Side B.

SIDE B

FIVE TRACKS, FIVE ARCS

Every track: behavior → test → RED → fix → GREEN

The main event. Five tracks, and each one runs the exact same loop. I'll describe a real user behavior, show the test that describes it, watch it fail against the broken app, fix the smallest possible thing, and watch it pass.

TRACK 01

FLOW

Keyboard navigation: the user journey through the review dialog

If it don't hang, then he can't bang
You can't hurt my feelings, but I like pain WAP — CARDI B FT. MEGAN THEE STALLION

Track 01 is flow — the journey. The behavior: a user opens a review with their keyboard, moves through the dialog, and leaves with Escape. Real users do this every day. If any part of the journey breaks, the flow breaks.

Track 01 — the behavior

A user opens the Illmatic review with the keyboard and:

  1. Focus lands inside the dialog when it opens
  2. Tab orbits inside the dialog — never the page behind
  3. Escape closes it and hands focus back to the trigger

Three sentences of behavior → three verses of test.

Notice what we don't say: no CSS classes, no component names, no implementation. Just the journey. That's a behavior — and behaviors are what users notice.

Track 01 — RED

The issue: the dialog forgets the keyboard exists.

  • Open the review — focus never lands inside the dialog
  • Tab — the cursor runs free across the page behind it
  • Escape — nothing happens, the dialog stays open

RED — 3/3 verses fail

Live demo: git checkout red-state in the demo repo, open the site, and show the broken behavior with the keyboard: focus stays on the trigger, Tab walks the whole page, Escape does nothing. Then run the track: npx playwright test tests/01-flow-keyboard-nav.spec.ts — all three fail. The tests were written for the behavior, so the broken behavior is caught the moment it happens — not when a user complains. The three verses: focus lands inside the dialog (getByRole('dialog') >> :focus expected 1, received 0), Tab orbits (12 presses, focus always inside), Escape closes and returns focus to the trigger.

Track 01 — the fix

One small hook restores the flow:

  • Focus in — the first control inside the dialog gets focus on open
  • Orbit — Tab wraps at the ends, never escapes the dialog
  • Escape — closes and hands focus back to the trigger

True story: my first version had a bug of its own — focus kept landing on the dialog container instead of a control. The same test caught it.

Live: fix the app — src/hooks/useFocusTrap.ts (focus lands, Tab orbits, Escape closes and returns focus). The subtle bug in my own fix: items[0]?.focus() ?? container.focus() — focus() returns undefined, so the fallback ALWAYS ran and refocused the container after the button. Track 01 caught it. Tests guard behavior — including the fixes.

Track 01 — GREEN

Run the same track again — the tests didn't change.

The app did.

GREEN — 3/3 pass

Tests describe behavior — the app earns its way to passing them.

Live: npx playwright test tests/01-flow-keyboard-nav.spec.ts — 3 passed. The same verses that caught the bug now guard the behavior forever. A future contributor who regresses the focus trap gets a red track automatically.

TRACK 02

HOOKS

Accessibility flows: the parts everyone sings back

And if the beat live, you know Lil Ju made it BODY — LIL JU PRODUCER TAG

Track 02 is hooks — the accessible parts of a song, the part everyone can sing back. For a site, that's the parts assistive tech can reach: proper dialog semantics, contrast, alt text. The hook fixture makes scanning effortless.

Track 02 — the behavior

A screen reader user opens a review and hears:

  1. A named dialog — announced as a modal, not a mystery box
  2. Content that passes WCAG 2.2 AA — contrast included
  3. Every cover described by its alt text

Accessibility is a behavior. Treat it like one.

Accessibility isn't a checkbox — it's a behavior real users depend on. We test it exactly like Track 01: describe the experience, assert it.

Track 02 — RED

The issue: invisible barriers for assistive tech.

  • The dialog is a plain div — no role, no name, nothing to announce
  • Footer text at 3.39:1 — under the 4.5:1 AA threshold

RED — the axe scan caught it

Live: run tests/02-hooks-accessibility.spec.ts — axe-core reports the footer contrast violation (fgColor #616161 on #000000, ratio 3.39, expected 4.5:1) and the dialog announces nothing: no role, no aria-modal, no accessible name. 2 of 3 verses red (alt text already passes). Real problems, caught by real assertions — not vibes.

Track 02 — the fix

  • Three attributes on the dialog: role="dialog", aria-modal, aria-labelledby the title
  • One color change: muted text #616161 → #8a8a8a — 3.39:1 → 5.7:1

Semantics are the hook of the web — give it something to grab.

Live: add role/aria-modal/aria-labelledby to the modal element in src/components/AlbumModal.tsx, and change the footer color in src/styles/index.css. The smallest fixes, verified by the same tests that caught them.

Track 02 — GREEN

Same scans, same assertions — new app.

GREEN — 4/4 pass

Anyone who strips the semantics or fades the text gets a red track — automatically.

Live: npx playwright test tests/02-hooks-accessibility.spec.ts — 4 passed. From here on, contrast regressions and dialog semantics are guarded by the suite.

TRACK 03

BARS

Visual stability: assertions that hold the layout to its word

Let's play a game, Simon says I'm still that bitch, ayy (Still that bitch)
I'm still that bitch, yeah SAVAGE — MEGAN THEE STALLION

Track 03 is bars — the lines that land. In design terms: the layout that holds its shape. A record doesn't jump forward when the snare hits, and a page shouldn't jump when an image finishes loading.

Track 03 — the behavior

A user on a slow connection scrolls the record bin and:

  1. Every card holds its box while covers stream in — no layout shift
  2. Every cover reserves its space from the first paint

Cumulative Layout Shift is a Core Web Vital. Bars measure it.

Layout shift isn't a cosmetic nit — it's a Core Web Vital (CLS). Users on slow networks click the wrong album because the grid moved under their cursor. The behavior: the layout must hold its shape no matter how covers load.

Track 03 — RED

The issue: covers push the page as they load.

  • On a slow connection, every card grows by one pixel when its cover arrives
  • The whole grid jumps — users click the wrong album

RED — 2/2 verses fail

Live: run tests/03-bars-visual-stability.spec.ts — the test slows covers by 1.5s via route interception, measures the card box before and after the cover loads: height 351.375 → 352.375. One pixel per card, every card, every load. Users feel it as a mis-click. The test found it because the assertion was written for the behavior, not for our own eyes.

Track 03 — the fix

  • The art box reserves its square up front — aspect-ratio: 1 / 1
  • The cover becomes an overlay on that box — it can't move the page

Cumulative Layout Shift is a Core Web Vital. Bars measure it.

Live: in src/components/AlbumArt.tsx / src/styles/index.css — aspect-ratio on the figure, absolute-positioned image with object-fit: cover. No layout for the image to participate in → the page can't shift. The bar holds.

Track 03 — GREEN

Same boxes, measured at the grid's worst moment.

GREEN — 2/2 pass

Live: npx playwright test tests/03-bars-visual-stability.spec.ts — 2 passed. A future contributor who drops the aspect-ratio gets a specific red track on every push.

TRACK 04

CADENCE

Resilient network handling: never stumble when the beat skips

スター、スター、スター、スター、キラキラ
私はスター MAMUSHI FT. YUKI CHIBA — MEGAN THEE STALLION

Track 04 is cadence — timing that never breaks, even when the beat skips. For the app: what happens when a cover request fails? A good MC keeps flowing. A good site keeps reviewing.

Track 04 — the behavior

A user on a flaky connection opens the record bin and:

  1. A dropped cover shows a fallback tile — never a broken-image icon
  2. The site keeps reviewing even when every cover fails

The beat will skip. Flow is what you do when it does.

Networks fail. Covers 404, requests drop, CDNs hiccup. The behavior we want: the site degrades gracefully — a styled fallback, never a broken icon.

Track 04 — RED

The issue: a dropped cover renders a broken-image icon.

  • Cut the network for one cover — the browser's broken icon appears
  • Cut it for all of them — sixteen broken tiles

RED — no fallback exists

Live: run tests/04-cadence-resilient-network.spec.ts — route interception aborts the cover request (madvillainy.jpg, then all covers). The app renders an img that goes nowhere: the browser's broken-image glyph. The test looks for the fallback tile and finds nothing. The behavior we designed for is missing, and the test knows it.

Track 04 — the fix

  • One error handler on the cover — on failure, swap to a fallback tile
  • The tile uses the album's own colors and keeps the title and artist

The beat will skip. Flow is what you do when it does.

Live: in src/components/AlbumArt.tsx — onError sets a failed flag; the failed render returns a gradient tile using the album's colors, labeled with title and artist. The review experience keeps flowing. Network-level testing: we're not mocking a library, we're cutting the actual request on the actual page.

Track 04 — GREEN

The site handles a total cover outage like a pro handles a skipped beat.

GREEN — 2/2 pass

Live: npx playwright test tests/04-cadence-resilient-network.spec.ts — 2 passed.

TRACK 05 · THE B-SIDE

LISTENER
FEATURES

Features real users touch: the tracklist, the rating, the comment thread

Every cipher has a B-side — the features nobody puts in the announcement but everyone actually uses. Here: the tracklist, a 5-mic rating that sticks, and a comment thread. All the pieces of an album people touch after the first play.

Track 05 — the behavior

A listener opens a review and wants to keep listening:

  1. The dialog shows the album's tracklist — the B-side of the record
  2. A 5-mic rating they set sticks — even after reload
  3. A comment they drop joins the thread — and stays

The features users touch are behaviors too. Test them like the rest.

The B-side is where the fun lives: persistence. The rating and the comment survive a reload — that's the behavior, and reload is how we prove it.

Track 05 — RED

The issue: the B-side is dead air — the features do nothing.

  • No tracklist in the dialog
  • Rating mics don't respond — no state, nothing sticks
  • There's no comment field — no thread to join

RED — 3/3 verses fail

Live: run tests/05-b-side-listener-features.spec.ts — the tracklist assertion finds nothing, the rating buttons don't exist, the comment field isn't there. The tests describe the features as behaviors, so the missing features are caught the moment the track runs.

Track 05 — the fix

  • Tracklist — render the album's data that already existed
  • Rating — clicks write through to localStorage, so it sticks
  • Comments — state plus the same persistence, so the thread joins

Same loop: behavior → test → RED → fix → GREEN.

Live: src/components/AlbumModal.tsx (tracklist + B-side row), RateAlbum.tsx (localStorage-backed rating), Comments.tsx (state + persistence). Nothing clever, nothing overbuilt.

Track 05 — GREEN

The B-side plays — and stays playing after reload.

The persistence tests reload the page and re-open the review — exactly what a listener does.

GREEN — 3/3 pass

Live: npx playwright test tests/05-b-side-listener-features.spec.ts — 3 passed.

OUTRO

FIVE BARS TO TAKE HOME

Thirty minutes of metaphor distilled into five bars you can take back to your own test suites on Monday.

Five bars to take home

  1. Flow — test the journey, not the page
  2. Hooks — one shared fixture, every verse drops into it
  3. Bars — assert behaviors, not implementation
  4. Cadence — wait for the real world; simulate its worst days
  5. No filler — every test earns its place on the album
Flow: if a human can't describe the journey, neither can the test. Hooks: setup is a fixture, not copy-paste. Bars: ask 'what does the user experience?', never 'what does the component render?'. Cadence: use route interception to test slow and broken networks. No filler: if a test never went red, it's proving nothing.

Write your own cipher

  1. Name your tracks after behaviors, not files
  2. One shared fixture — the hook — for setup
  3. Write the behavior in plain language first
  4. Watch it go RED before you write the fix
  5. Fix the smallest thing that restores the flow
  6. Watch it go GREEN — then keep it green in CI
A six-step checklist. The red step is the one people skip — but the red run is what proves the test actually guards the behavior. If it never went red, you don't know it can catch anything.
