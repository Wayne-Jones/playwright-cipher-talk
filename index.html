SIDE A

THE CIPHER

A cipher: a circle of emcees, one microphone. Each person takes a turn with the mic, spits a verse, passes it on. If anyone drops a weak verse, the whole circle feels it. That's our test suite.

The Four Concepts of Rap

  • Each verse has flow — the rhythm of the journey
  • A hook — the part everyone sings back
  • Bars — the lines that land and stay with you
  • Cadence — timing so good nobody stumbles

"A good cipher has no filler. Every line earns its place."

Rap should contain no filler, making every test earn its place in your test suite. How do these four concepts of rap translate to testing?

The metaphor map

Rap Playwright
Cipher Test suite
Verse A single test
Flow The user journey the test walks
Hook Fixtures & helpers
Bars Assertions
Cadence Reliable waiting & network resilience
Flow is the journey your test walks — the same path a user walks. Hooks are the fixtures and helpers that set up the test. Bars are the assertions, the lines that land. Cadence is the timing: waiting reliably for the app, not sleeping through it.

Why we need the structure

Too many test suites are like an off-beat freestyle:

  • Tests nobody can read — 400 lines of setup
  • Tests that are flaky — they pass alone, fail in CI
  • Tests that assert implementation, not behavior
Having your tests structured like a cipher would fix all three situations: Making things readable (Utilizing fixtures and patterns), resilient (behavior-level waits, cadence), and maintainable (every test has a purpose and tests behavior).

SIDE B

FOUR TRACKS

behavior → test → RED → fix → GREEN
For each test that I'll go over, I'll describe a real user behavior, show the test that describes it, watch it fail against the broken app, fix the smallest possible thing, and watch it pass. This is the basis of Test Driven Development (TDD)

TRACK 00

SOUND CHECK

Before the album plays, the room gets a sound check.

Smoke Tests is your minimum viable test

Your sound check is your smoke tests. If your sound check fails, the show doesn't go on - and that's the point of the smoke test. With smoke tests, we answer the simple question? Does your application load correctly with the behavior we expect?

TRACK 01

FLOW

The user journey through the review dialog

Track 01 will go through a typical user behavior through our application.

Track 01 — The Behavior

A user opens the Illmatic review modal:

  1. Users are able to rate the album art via a mic rating
  2. Users are able to leave a comment in the comment box, submit and see their submission

Two sentences of behavior → two verses of tests.

The behavior is the user journey through the review modal. The first verse tests the mic rating, the second tests the comment box. Each verse is a test that describes a user behavior, not an implementation detail.

TRACK 02

HOOKS

Utilizing Fixtures and Page Object Model Pattern for readability

Hooks are the parts that everyone sings back. In testing, hooks are the fixtures and helpers that set up the test. In our demo, we will go over utilizing fixtures to make tests easier to read and maintain. Fixtures are a way to set up the test environment and provide reusable components for the tests. The Page Object Model (POM) pattern is a design pattern that helps to create an abstraction layer for the UI elements, making the tests more readable and maintainable.

Track 02 — The Behavior

A user utilizes the keyboard to navigate the website:

  1. We need to test that when opening the modal, the focus is on the first interactive element in the modal.
  2. We need to make sure when the modal is open, focus cycles through the modal and does not escape to the background page.
  3. When pressing escape, we need to test that the modal closes and focus returns to the element that opened the modal.

Accessibility is a behavior. Treat it like one.

TRACK 03

BARS

Visual stability makes sure the layout holds to it's word

Visuals are just as important as functionality. When pages load we need to make sure that there is no cumulative layout shift so that cards don't jump around.

Track 03 — The Behavior

A user on a slow connection navigates to our website:

  1. Need to make sure that every card holds it's box while covers stream in - minimizing layout shift

Cumulative Layout Shift is a Core Web Vital. Bars measure it.

Layout shift isn't a cosmetic nit — it's a Core Web Vital (CLS). With bad CLS, users on slow networks could accidentally click the wrong album because the grid moved under their cursor. This test measures the CLS score of the page and fails if it exceeds a threshold.

TRACK 04

CADENCE

Resilient network handling: never stumble when the beat skips

Metaphor: reliable waiting & network resilience

Track 04: cadence. When the network skips out — that's where cadence matters. A good MC keeps flowing; a good site degrades gracefully. Here I cut the request to see the failure mode, then restore it. Run tests/04-cadence-resilient-network.spec.ts.

Track 04 — The Behavior

A user on a flaky connection opens the record bin and:

  1. A dropped cover shows a fallback tile — never a broken-image icon
  2. The site keeps reviewing even when every cover fails

The beat will skip. Flow is what you do when it does.

Track 04: cadence — timing that never breaks. The behavior: when a cover request fails, the site degrades gracefully — a fallback tile, never a broken icon. In the demo we run: npx playwright test tests/04-cadence-resilient-network.spec.ts — every aborted cover renders a placeholder.

FOUR BARS TO TAKE HOME

Twenty-five minutes of metaphor distilled into four bars you can take back to your own test suites on Monday.

Four bars to take home

  1. Flow — test the journey, not the page
  2. Hooks — one shared fixture, every verse drops into it
  3. Bars — assert behaviors, not implementation
  4. Cadence — wait for the real world; simulate its worst days
